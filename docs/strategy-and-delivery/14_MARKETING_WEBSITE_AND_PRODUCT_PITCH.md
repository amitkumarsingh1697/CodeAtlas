# Marketing, Website & Product Pitch

## 1. Messaging hierarchy
### Primary headline
Understand complex software before you change it.

### Subheadline
CodeAtlas analyzes existing repositories locally and maps architecture, dependencies and data relationships with evidence, coverage and explicit uncertainty.

### Supporting proof points
- Local-first analysis.
- Evidence-labelled relationships.
- Source-level provenance.
- Coverage and unresolved findings.
- Architecture and change-impact exploration.
- Consultancy-ready reports.

Only publish a proof point after the corresponding capability passes release and accuracy gates.

## 2. Website structure
1. Hero: headline, subheadline, request assessment CTA.
2. Problem: unfamiliar systems, stale documentation, discovery effort.
3. How it works: select repository → analyze locally → explore evidence → export report.
4. Product screenshots/video.
5. Evidence model: observed/inferred/unknown.
6. Security and deployment.
7. Supported languages/frameworks with maturity levels.
8. Assessment offer and sample report.
9. FAQ and limitations.
10. Contact / request assessment.

## 3. CTA
Primary: Request an Architecture Assessment.  
Secondary: View a Sample Report / Try the Local Core.

## 4. 30-second pitch
“CodeAtlas helps engineering teams and modernization consultancies understand unfamiliar software systems without sending source code to a third-party service. It builds an evidence-backed view of architecture, dependencies and data relationships, shows what is observed versus inferred, and produces a report teams can use before modernization or major changes.”

## 5. 2-minute product pitch
“Most teams inherit systems they did not build. Documentation may be incomplete, dependencies are difficult to trace, and architecture discovery consumes senior engineering time. CodeAtlas runs locally against an authorized repository. It inventories the system, extracts supported relationships, links findings to source evidence and makes gaps visible. Teams can explore the architecture and export a client-ready assessment. We start with modernization consultancies because they repeatedly face this problem across client engagements. We are validating both TypeScript/PostgreSQL and Java/Spring capabilities independently, and we publish measured coverage rather than claiming complete understanding.”

## 6. Demo story
Use one repository with documented ground truth. Show:
- scan scope and local execution;
- coverage;
- architecture overview;
- search;
- one observed edge and one inferred edge;
- source evidence;
- impact workflow;
- report export;
- explicit limitations.

## 7. Claims policy
Never use:
- “understands any codebase”;
- “100% accurate”;
- “guaranteed safe changes”;
- “all dependencies”;
- “zero data leaves” unless technically verified across all flows;
- “SOC 2/ISO certified” without certification.
Prefer “supported repository types,” “measured benchmark,” “local-first core analysis,” “evidence-backed findings,” and “known limitations shown.”
